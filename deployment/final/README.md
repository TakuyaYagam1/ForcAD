# Профиль `pr-final`

Профиль рассчитан на VM с 8 vCPU и 16 GiB RAM, шесть игровых команд и одну
NPC-команду. Это статический бюджет, а не доказательство производительности.
Допуск требует репетиции с реальными чекерами, сервисами и мониторингом.

## Ресурсы вулнбоксов

Каждому вулнбоксу в обоих дивизионах выделять 4 vCPU / 4 GiB RAM,
включая NPC. Для ПР это 7 × 4 / 4 = 28 vCPU / 28 GiB. Вместе с
ForcAD 8 / 16, Router 2 / 4 и VPN 2 / 2 бюджет ПР составляет
40 vCPU / 50 GiB. Бюджет ЧР (22 вулнбокса, ForcAD 24 / 32,
Router 4 / 8, VPN 2 / 4) составляет 118 vCPU / 132 GiB.
Итого два дивизиона требуют 158 vCPU / 182 GiB при 128 физических
ядрах / 240 GiB RAM: CPU переподписан на 30 vCPU. Эти значения
задаются в Proxmox для VM, а не в Compose ForcAD.

## Нагрузка чекеров

Игра содержит 240 раундов по 60 секунд:

| Сервис | PUT | GET | CHECK |
| --- | ---: | ---: | ---: |
| kincare | 5 | 3 | 1 |
| wahrwelt | 10 | 1 | 1 |
| sentinel | 3 | 3 | 1 |
| На команду | 18 | 7 | 3 |

Верхняя граница составляет 28 действий на команду и 196 действий на раунд
для семи команд. Два worker по восемь action slots дают 16 слотов. Нижняя
оценка работы пула равна `196 * среднее время действия / 16`:

| Среднее действие | Работа пула на раунд |
| ---: | ---: |
| 1 с | 12.25 с |
| 2 с | 24.5 с |
| 3 с | 36.75 с |
| 5 с | 61.25 с |
| 10 с | 122.5 с |
| 20 с | 245 с |

При 50% средней занятости среднее действие должно занимать не более 2.45 с.
Расчет не учитывает порядок CHECK/PUT/GET, ожидание сети, закрепление workflow
за worker, CPU запуска Python, БД и очереди. Поэтому 16 слотов сами по себе не
доказывают завершение раунда за 60 секунд. На 8 vCPU такая конкуренция
предполагает заметную долю ожидания I/O; CPU-bound чекеры нужно измерить.

Лимит адресного пространства каждого checker-процесса оставлен равным
1024 MiB. Hard limit каждого worker равен 3 GiB, а `GOMEMLIMIT` процесса Go -
384 MiB. Восемь дочерних процессов могут суммарно превысить контейнерный
лимит, если их реальный RSS велик. Это риск OOM, который нужно проверить на
реальных чекерах. Не уменьшать per-process limit без измерений, доказывающих,
что меньший предел безопасен.

## База данных

| Роль | Реплики | pgx на реплику | pgx всего | PgBouncer servers | Alias clients |
| --- | ---: | ---: | ---: | ---: | ---: |
| API | 2 | 8 | 16 | 16 | 32 |
| Receiver | 1 | 16 | 16 | 16 | 32 |
| Worker | 2 | 8 | 16 | 16 | 32 |
| Ticker | 1 | 4 | 4 | 4 | 16 |
| Итого | | | 52 | 52 | |

К каждому alias калькулятор добавляет восемь резервных клиентов. Требование
PgBouncer равно 84 клиентам при глобальном лимите 128. PostgreSQL имеет
`max_connections=80`: после 52 серверных соединений PgBouncer остается 28,
в том числе обязательный запас 16 для инициализации, мониторинга и
администрирования. Эти бюджеты нужно пересчитать при изменении реплик или
пулов.

## Память

Все долгоживущие контейнеры имеют ненулевой hard limit. Сумма hard limits
равна 13.5 GiB, поэтому из 16 GiB остается 2.5 GiB гостевой ОС, Docker и
кратковременным пикам.

| Компонент | Soft reservation, GiB | Hard limit, GiB |
| --- | ---: | ---: |
| 2 API | 1 | 1.5 |
| Receiver | 0.5 | 0.75 |
| 2 worker | 4 | 6 |
| Ticker | 0.125 | 0.25 |
| Nginx | 0.125 | 0.25 |
| PostgreSQL | 1.5 | 2 |
| Redis | 0.25 | 0.5 |
| NATS | 0.25 | 0.5 |
| PgBouncer | 0.125 | 0.25 |
| Prometheus | 0.5 | 1 |
| Grafana | 0.25 | 0.5 |
| Итого | 8.625 | 13.5 |

Soft reservation не выделяет память заранее. Hard limit ограничивает
контейнер, но не гарантирует, что рабочая нагрузка поместится в него.
`GOMEMLIMIT` управляет сборщиком мусора Go и не ограничивает дочерние
checker-процессы. Одноразовые initializer, config-loader, postgres-data и
checker-db-access не входят в сумму долгоживущих контейнеров; во время старта
они дополнительно используют оставшийся запас.

Prometheus ограничен 1 GiB RAM, retention 3 дня / 2 GB, четырьмя параллельными
запросами и одним миллионом samples на запрос. Grafana ограничена 512 MiB.
Такие пределы защищают игру от неконтролируемого роста мониторинга, но тяжелые
панели могут завершаться ошибкой. Мониторинг должен оставаться включенным во
время репетиции.

## Применение

Единственный selector профиля - `pr-final`. Renderer должен использовать
`env.capacity = "pr-final"`. Для ручного deployment перенести значения из
`deployment/final/limits.env.example` в приватный
`deployment/docker/.env`, не заменяя существующие адреса, branding и секреты.
После изменения environment контейнеры нужно пересоздать, а не только
перезапустить.

Compose defaults и `limits.env.example` совпадают по репликам, пулам и памяти.
Калькулятор рендерит основной Compose вместе с monitoring overlay и возвращает
ненулевой код при нарушении replica, connection или memory budget:

```sh
python3 deployment/final/capacity.py
python3 -m unittest discover -s deployment/final -p 'test_capacity.py' -v
```

`capacity.json` является сохраненным расчетом текущего профиля. Реальные
пароли Grafana и reader БД должны оставаться только в приватном `.env`.

Исходники `checkers/{kincare,wahrwelt,sentinel}/` не отслеживаются Git.
Перед рендерингом передать приватные файлы чекеров на хост рендера и
на целевой хост установки; без них проверка путей остановит сборку.

## Репетиция и допуск

`rehearse.sh` использует selector `pr-final`, семь команд, 42 синтетических
наблюдателя (шесть игровых команд по семь участников), 2 API, 1 receiver,
2 worker по 8 слотов и monitoring. Load fixture выполняет только один GET на
сервис, тогда как реальная верхняя граница PFR в `capacity.py` использует
3/1/3 GET для kincare/wahrwelt/sentinel. Поэтому репетиция недооценивает
GET-нагрузку и даже ее PASS не доказывает реальные 60-секундные раунды.

```sh
./deployment/final/rehearse.sh checker
./deployment/final/rehearse.sh combined
./deployment/final/rehearse.sh soak
```

Перед игрой проверить минимум:

- завершение каждого раунда без потерянных CHECK/PUT/GET и просроченных jobs;
- p95/p99 действий, возраст очереди, CPU и RSS каждого checker;
- OOM/restart/throttling всех контейнеров и `MemAvailable` гостевой ОС;
- ожидание pgx/PgBouncer, PostgreSQL locks/WAL/fsync и свободное место;
- доступность Prometheus/Grafana и ошибки запросов панелей.

Профиль не содержит измеренного обещания throughput и не гарантирует
60-секундные раунды. При нехватке CPU или RAM сначала уменьшать предложенную
нагрузку и измерять узкое место, а не скрывать проблему увеличением timeout.
Для отката восстановить сохраненный приватный `.env` и пересоздать контейнеры;
схема БД этим профилем не меняется.
