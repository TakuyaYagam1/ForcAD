# Финал CHRP

Настройки ветки `chrp-final` рассчитаны для репетиции на 28 команд. Готовность
к финалу требует совместного прогона на целевом сервере с финальными чекерами.
Увеличение лимитов само по себе такую готовность не доказывает.

## Исходные данные

| Параметр | Значение |
| --- | --- |
| Команды / участники | 28 / 196 |
| Вулнбоксы | 28 отдельных машин, каждая 4 CPU / 8 ГБ |
| Сервисы | 3 на команду, 40 flag places суммарно |
| Игра | 300 раундов по 60 секунд, 5 часов |
| Жизнь флага | 5 раундов |
| ForcAD | 64 GiB RAM, заявленные 24 ядра / 32 потока |
| Router / VPN | По 16 GiB RAM и 8 ядер |
| Репетиция | i9-13900KF / 32 ГБ RAM |

Предполагается `puts = places`, `gets = 1` для каждого сервиса,
`checker_timeout = 20`, `extra_checks = 0`. Распределение 14/13/13 в шаблоне
условное. Заменить его реальными places и путями к чекерам перед рендерингом.
Ресурсы 28 вулнбоксов выделяются отдельно от ForcAD, Router и VPN.

## Емкость чекеров

За раунд: 84 CHECK + 1120 PUT + до 84 GET = до 1288 запусков процессов.
Некоторые GET пропускаются, если в выбранном раунде еще нет флага.
За игру: до 386400 действий, 25200 workflow и 336000 созданных флагов.
Текущая SQL-проверка включает границу `round >= current_round - flag_lifetime`:
при жизни 5 это до 6 номеров раундов с текущим, то есть до 6720 живых флагов.
Истечение срока не означает немедленное физическое удаление записей из БД.

20 worker x 8 действий = 160 слотов. Необходимая работа пула в секундах:
`1288 x среднее время действия / 160`. Это нижняя граница длительности раунда:
CHECK должен закончиться до PUT/GET, GET идут последовательно, задания
закреплены за worker, а публикация, БД и CPU добавляют задержки.

| Среднее действие | Работа пула за раунд | Средняя занятость слотов |
| --- | --- | --- |
| 1 с | 8.05 с | 13.4% |
| 2 с | 16.1 с | 26.8% |
| 3 с | 24.15 с | 40.3% |
| 5 с | 40.25 с | 67.1% |
| 10 с | 80.5 с | Не укладывается |
| 20 с | 161 с | Не укладывается |

Для 50% средней занятости нужно средневзвешенное время действия не выше
3.73 с. Отдельно измерять CPU-секунды: занятый слот часто ждет сеть, но запуск
Python и работа самого чекера расходуют CPU. Все таймауты одновременно в
минутный раунд эта конфигурация не вмещает. Увеличение числа процессов при
насыщенном CPU может только увеличить задержки.

Цель репетиции: все 84 workflow и все 1120 PUT каждого завершенного раунда
сохранены, статус 101, без таймаутов и заданий, перешедших за границу раунда.
Для запаса желательно завершать нормальный раунд за 30 секунд. Проверять
также p95/p99, максимальный возраст открытого задания и длительность CHECK.
`gets = 1` не проверяет каждый живой флаг в каждом раунде.

Существующий базовый предел адресного пространства отдельного чекера
сохранен: 1024 MiB, как до настройки финала. Это не RSS и не резерв RAM.
Дополнительного hard limit на контейнер worker нет. Пиковый RSS чекеров
измерять вместе с Go и дочерними процессами; 160 одновременно запущенных
чекеров не означают заранее выделенные 160 GiB. Добавленное ранее ограничение
GOMAXPROCS=2 убрано; Go выбирает параллелизм автоматически.

## Соединения и запросы

| Роль | Реплики | pgx / реплику | Клиенты pgx всего | Серверы PgBouncer всего |
| --- | --- | --- | --- | --- |
| API | 4 | 16 | 64 | 32 |
| Receiver | 4 | 16 | 64 | 64 |
| Worker | 20 | 4 | 80 | 32 |
| Ticker | 1 | 8 | 8 | 8 |
| Итого | 29 | | 216 | 136 |

PgBouncer разделяет роли по alias, поэтому прием флагов не забирает серверный
пул worker. Лимит каждого alias в этом профиле 256 клиентов; глобальный 1024.
В новой основе ветки бюджет клиентов проверяется и учитывает реплики, а
команды масштабирования проверяют его перед изменением числа контейнеров.
PostgreSQL ограничен 200 соединениями: после 136 серверов pooler остается
64 на администрирование, reader Grafana, инициализацию и запас. Несколько
pooler на разных хостах требуют суммировать их серверные бюджеты заново.

Redis: до 29 x 32 = 928 клиентских соединений приложений при потолке 10000.
NATS JetStream: 20 worker-подключений, до 8 полученных jobs на worker и до 160
jobs в обработке на ферму. Общий durable consumer имеет `MaxAckPending=1024`;
это общий предел фермы, а не число слотов одной реплики. Подтверждение идёт после
фиксации результата в SQL, повторная доставка защищена SQL claim/lease.
Это не дополнительные 160 action slots: один workflow содержит
несколько действий, а семафор worker общий для всех его заданий.

API допускает 1024 одновременных REST-запроса, receiver 512 запросов.
RPS и одновременные соединения различаются. При 10000 RPS и среднем времени
ответа 50 мс занято примерно 500 HTTP-слотов; при 200 мс уже 2000. Размер пула
не компенсирует медленную БД или остановку CPU. При насыщении 503 остается
управляемым отказом, который нужно учитывать в критериях репетиции.

Nginx сохраняет 8192 соединения на worker и nofile 65536. Проксируемый запрос
занимает клиентский и upstream-сокет; keepalive и WebSocket тоже занимают
слоты. Это не глобальный предел всей системы. При 196 участниках даже четыре
вкладки на человека дают 784 WebSocket, по два сокета Nginx на подключение.
Потолок WebSocket у четырех API суммарно 8192. Nginx worker с большим числом
долгих соединений все равно нужно проверять отдельно на равномерность нагрузки.

Лимиты REST 150 RPS/IP и `/flags` независимы. Лимит флагов 200 значений/с на
команду, burst 400, суммарно 5600 значений/с. Пакет из 100 стоит 100 единиц.
При полном захвате всех флагов всеми соперниками в среднем появляются
`1120 x 27 / 60 = 504` новых засчитываемых сдачи в секунду, всего до 9072000
за игру. Повторы и случайные значения могут создать гораздо больше запросов.
10000 REST RPS, 10000 запросов `/flags` и 10000 флагов/с являются разными
сценариями. Штатные 429 при превышении командного бюджета не являются
ошибкой расчета сокетов; сдающим клиентам нужны batching, backoff и retry.

Ответ `attack_data` при 6720 PFR-подсказках может занимать сотни килобайт.
Например, 40 байт на подсказку дают примерно 269 KB без полного JSON overhead.
Если этот endpoint получает шестую часть 10000 REST RPS, только его полезная
нагрузка составляет около 448 MB/s, или 3.6 Gbit/s. Для реальной схемы нужно
измерить размер ответа, частоту polling и при необходимости опрашивать
`attack_data` с фильтром одного сервиса. Прежние 10k RPS на маленьких ответах
не подтверждают эту нагрузку. Финальные fixtures используют PFR, а лимит
читаемого генератором ответа увеличен до 1 MiB, чтобы не обрезать такой JSON.

## Память и диск

Контейнеры используют мягкие reservations и могут брать память сверх них.
Значения `FORCAD_*_MEMORY=0` отключают hard limits памяти.

| Компонент | Soft reservation суммарно, GiB |
| --- | --- |
| 20 worker | 15 |
| 4 API | 2 |
| 4 receiver | 2 |
| PostgreSQL | 4 |
| Redis / NATS | 0.5 / 0.5 |
| PgBouncer / Nginx / Ticker | 0.125 / 0.125 / 0.125 |
| Prometheus / Grafana | 2 / 0.5 |
| Итого долгоживущие контейнеры | 26.875 |

Это не потолок потребления и не предвыделение памяти. Рабочий ориентир для
мониторинга остается до 56 GiB на процессы и данные с целевым запасом около
8 GiB хосту, но контейнеры им не ограничены. Фактический остаток определяется
измерениями; калькулятор возвращает `null` для общего hard ceiling и headroom,
когда память не ограничена. Сверить MemTotal и доступную Docker память.

Soft reservations не выделяют память заранее и не гарантируют ее получение.
Стартовые контейнеры используют память дополнительно, до начала игры.
`GOMEMLIMIT` ограничивает поведение Go GC, а не всю память контейнера и не
дочерние процессы. PostgreSQL получает shared_buffers 2 GiB; остальные запросы,
WAL и память backend учитывать по фактическому потреблению. Durable commit сохранен.

32 ГБ не подтверждают запас памяти 64 GiB сервера. Без hard limits рост
потребления требует контроля хостовой RAM. На финальном хосте не размещать
генератор нагрузки или вулнбоксы. Суммарный диск рассчитывать по фактическим
`pg_total_relation_size`, объему WAL и приросту accepted steals: 9 млн строк
со связанными индексами существенно больше 336 тыс. строк Flags.
Практический стартовый бюджет - 200 GiB свободного SSD/NVMe с контролем
скорости WAL fsync и роста БД. Проверить его пятичасовым прогоном, не считать
этот объем измеренным размером финальной БД.

Логи контейнеров ротируются, 10 MiB x 3 файла. Их хранение ограничено;
необходимые логи выгружать во время репетиции. Prometheus имеет retention
7 дней / 16 GB и soft reservation 2 GiB без RAM cap. Retention ограничивает историю, а не всю
пиковую RAM и не все место под WAL/head. Оставить место сверх 16 GB.

## Мониторинг, Router и VPN

Grafana не обрабатывает каждый игровой HTTP-запрос. Она запрашивает Prometheus
и reader PostgreSQL. Сейчас в репозитории шесть дашбордов с 55 панелями и
refresh 15 с. Для семи открытых вкладок нагрузка определяется запросами панелей,
временным диапазоном и числом операторов. При условных 10 запросах на вкладку
это около 4.7 запроса/с на оператора, а не 10000 запросов/с к Grafana.
В репетиции открывать нужные вкладки и диапазоны одновременно с нагрузкой.

Prometheus scrape/evaluation остаются 15 с; query concurrency 8, max samples
5 млн. Reader Grafana ограничен двумя соединениями, запросом 3 с и lock wait
500 мс, read-only. Тяжелая панель может получить ошибку вместо длительного
удержания ресурсов игры. Проверка интеграции Grafana прошла на локальном
стенде, но семь вкладок под финальной нагрузкой еще не измерены.

Метки Zeek ограничены парами команд: 28 x 28 = 784 пары на семейство, плюс
196 peer mappings. Число RPS увеличивает counters, а не создает ряд на каждый
запрос. Сенсор работает одним процессом: его packet processing не становится
восьмипоточным от наличия восьми ядер у Router. Финальный bundle дает Zeek
MemoryHigh 4 GiB, MemoryMax=infinity, CPUWeight=10 и Nice 10. Это мягкое
давление по памяти и приоритет CPU, без жесткой CPU quota. При capture drops
и stream gaps сначала измерять packets/s,
байты/с, CPU и receive drops. Если одного процесса недостаточно, нужен отдельный
flow-balanced Zeek cluster/сенсор с повторной проверкой агрегации метрик.
Просто поднять CPUQuota многопоточность не добавит.

Сенсор считает HTTP/1, TCP/UDP и WebSocket upgrades. Он не хранит полные PCAP
и отключает стандартные protocol logs/file extraction. Потерянные пакеты,
шифрование и асимметрия маршрутов ограничивают видимость. Работу сервиса
подтверждают также чекер и его логи, а не только сетевые counters.

Для 7 участников генератор выделяет /28 каждой команде. Пул
10.183.200.0/23 вмещает 32 блока, из них используются 28; admin VPN перенесен
в 10.183.202.0/24. Старые конфигурации до 5 участников сохраняют /29.
Изменение числа участников с 5 на 7 меняет адреса и WireGuard-конфигурации:
потребуется новый bundle и новые клиентские конфиги.

`host.sysctl.conf` содержит предлагаемые значения для выделенных хостов.
Они не применяются автоматически и не меняют существующую политику
восстановления installer. Перед применением загрузить nf_conntrack, сохранить
старые значения и проверить отсутствие конфликта владельцев файлов sysctl.
Потолок conntrack 4194304 не предвыделяет все записи. При 10000 новых TCP/с
и 120 с удержания хвоста получается около 1.2 млн записей; реальные established
timeouts, UDP, NAT и пакеты меняют оценку. Проверять count/max, slab, NIC drops,
`ss -s`, `nstat`, `ip -s link`, `ethtool -S` на каждом хосте.
При среднем ответе 10 KB поток 10000 RPS требует около 800 Mbit/s только
полезной нагрузки. Размеры ответов и встречный трафик могут потребовать
больше пропускной способности. RPS не заменяет измерение сети.

## Применение

Шаблон инфраструктуры: `infrastracture/settings.final.example.toml`.
Подставить реальные команды, интерфейсы, WAN/VPN endpoint, порты трех сервисов,
чекеры и дату старта. С placeholders checker renderer намеренно откажется
работать. `env.capacity = "chrp-final"` добавляет `limits.env.example` в
сгенерированный environment. Установка выберет ветку `chrp-final`; перед
финалом лучше закрепить проверенный commit SHA вместо движущейся ветки.
Для установки из Git использовать опубликованную ветку chrp-final.

Для ручной установки перенести пары ключ/значение из `limits.env.example`
в `deployment/docker/.env`, сохранив существующие branding, адреса и секреты.
Затем использовать обычный `./control.sh monitoring ...`. Изменения env
требуют recreate контейнеров, а не простого restart. YAML игры применяется
при инициализации новой БД; редактирование YAML не меняет начатую игру.
Этот профиль не применялся к существующему игровому deployment.

```sh
python3 deployment/final/capacity.py
python3 -m unittest discover -s deployment/final -p 'test_*.py' -v
```

Калькулятор читает рендер Compose без загрузки secret env files, ничего не
поднимает и возвращает ненулевой код при несогласованных лимитах.
`capacity.json` содержит сохраненный расчет текущего профиля.

## Репетиция на i9

Нужны Linux/WSL, Docker Compose, Go из backend/go.mod, Python 3 и Make.
Генератор и приложение на одном хосте конкурируют за CPU/RAM, поэтому итог
содержит также стоимость самого генератора. Закрыть лишние приложения и
контролировать физическую память хоста, включая Windows при WSL.

```sh
./deployment/final/rehearse.sh checker
./deployment/final/rehearse.sh combined
./deployment/final/rehearse.sh soak
```

Первый прогон: 15 минут, 100 REST RPS, 2 flag batch/s. Второй: 15 минут,
10000 REST RPS и 40 flag batch/s по 100 значений. Третий повторяет второй
пять часов без промежуточных пауз. У всех: 28 команд, три синтетических
сервиса, 40 PUT на команду, 20 worker x 8, 224 WebSocket-наблюдателя,
Prometheus/Grafana и проверка каждого завершенного раунда. Преднамеренный
flag-burst этап отдельно проверяет превышение rate limit.
У fixtures нет round limit, поэтому warmup и recovery могут добавить раунды
сверх пятичасового непрерывного участка.

Отчеты сохраняются в `backend/load_test/reports/`. Тест создает собственный
Compose-проект с новой БД, а после завершения удаляет только свой стенд.
Адреса Grafana/Prometheus печатаются при старте; для просмотра нужны временные
доступы из runtime-файла этого тестового проекта, не логин основного стенда.

Адаптер изолированного теста представляет клиентов через X-Forcad-Load-Client
и сохраняет для каждого корзину 150 RPS/burst 60. Production image и рабочая
проверка реального IP не изменены. Тест распределяет 10000 REST RPS по 224
корзинам, поскольку один адрес намеренно получил бы 429. Реальную атрибуцию
196 WireGuard IP и отсутствие общего SNAT проверить через Router/VPN отдельно.

Этот прогон проверяет платформу с fixtures. Он не заменяет репетицию трех
финальных сервисов на вулнбоксах 4 CPU / 8 ГБ и packet replay на Router с Zeek.
Новый совместный сценарий здесь не запускался после решения перенести
нагрузочные тесты на i9. Известные локальные неуспешные прогоны сохранены в
`validation.md`. Увеличивать deadline теста ради PASS нельзя.

## Допуск и откат

Допуск: минимум один совместный пятичасовой прогон без неожиданных HTTP
429/503, timeouts, пропущенных PUT, неучтенных accepted steals, остановки
раундов, OOM, постоянного ожидания пулов и capture drops. Generator_valid
должен быть true. Проверить одновременно панели Grafana и запас ресурсов,
включая NVMe, хостовый conntrack и все три сервиса каждого вулнбокса.

Откат настроек до игры: восстановить сохраненный `.env`, вернуть прежние
параметры capacity и пересоздать контейнеры теми же control-командами.
Схема БД этой работой не менялась; данные не удалять. Между версиями основы
репозитория совместимость схемы проверять отдельно. WireGuard и sysctl
откатывать из сохраненных конфигов и значений, не генерировать новые ключи
повторным renderer поверх установленного deployment.

Источники: [PgBouncer](https://www.pgbouncer.org/config.html),
[Prometheus storage](https://prometheus.io/docs/prometheus/latest/storage/),
[Zeek cluster](https://docs.zeek.org/en/current/frameworks/cluster.html).
