# Репетиция финала ЧР

Актуальная конфигурация: 21 игровая команда и NPC, три сервиса
(`kincare`, `wahrwelt`, `sentinel`), 240 раундов по 60 секунд. На VM
24 vCPU / 32 GiB запускаются 4 API, 2 receiver и 4 worker по 8
action slots. Профиль: `deployment/final/limits.env.example`;
расчёт из Compose: `python3 deployment/final/capacity.py`.

Каждому из 22 вулнбоксов ЧР, включая NPC, выделять
4 vCPU / 4 GiB RAM, как и вулнбоксам ПР.

Реальная верхняя граница нагрузки - 22 × (3 CHECK + 18 PUT + 7 GET) =
616 действий за раунд. Для 32 слотов даже без сетевых задержек и
зависимостей CHECK → PUT/GET среднее действие в 3 с займёт не меньше
57.75 с. Мягкие резервации занимают в сумме 13.875 GiB, но hard limits
отключены: вместимость 32 GiB и соблюдение 60 секунд не доказаны.

`./deployment/final/rehearse.sh checker` запускает изолированную
синтетическую репетицию; `combined` добавляет REST-нагрузку, `soak` -
длительный прогон. Тестовый fixture делает один GET на сервис вместо
реальных 3/1/3. Результат репетиции сам по себе не подтверждает время
раунда с настоящими сервисами и чекерами; перед игрой измерить его на
целевой VM.

## Бюджет двух дивизионов

| VM | ЧР, vCPU / GiB | Количество ЧР | ПР, vCPU / GiB | Количество ПР |
| --- | ---: | ---: | ---: | ---: |
| ForcAD | 24 / 32 | 1 | 8 / 16 | 1 |
| Router | 4 / 8 | 1 | 2 / 4 | 1 |
| VPN | 2 / 4 | 1 | 2 / 2 | 1 |
| Вулнбокс, включая NPC | 4 / 4 | 22 | 4 / 4 | 7 |
| Суммарно | 118 / 132 | | 40 / 50 | |

Оба дивизиона требуют 158 vCPU / 182 GiB RAM: при 128 физических ядрах
vCPU переподписаны на 30. CPU и RAM VM (включая Router, VPN и вулнбоксы)
задаются в Proxmox; Compose управляет только контейнерами ForcAD.
Раздельные VLAN/маршрутизация и запрет доступа между дивизионами должны
быть настроены на инфраструктуре; эти профили их не создают.

## Подключение профиля

`infrastracture/settings.final.example.toml` перечисляет 21 игровую
команду ЧР, NPC, три финальных сервиса и 240 раундов. Перед рендерингом
подставить реальные адреса, WAN/VPN endpoint и интерфейсы. Исходники
чекеров не хранятся в Git; файлы `checkers/{kincare,wahrwelt,sentinel}/`
передать отдельно на хост рендера, иначе проверка путей остановит сборку.
Путь `revision = "chrp-final"` перед установкой заменить на проверенный
commit SHA; отдельный Git checkout на целевом хосте также должен получить
приватные файлы чекеров.

`env.capacity = "chrp-final"` подключает
`deployment/final/limits.env.example` при рендеринге. При ручной
установке перенести его значения в приватный `deployment/docker/.env`,
сохранив адреса, брендинг и секреты. Для применения изменённого
environment контейнеры нужно пересоздать; редактирование config.yml
не изменяет игру в уже инициализированной БД.

```sh
python3 deployment/final/capacity.py
python3 -m unittest discover -s deployment/final -p 'test_capacity.py' -v
```

Калькулятор рендерит Compose, проверяет бюджеты пулов, реплик и памяти,
но не запускает контейнеры и не доказывает укладывание раунда в 60 с.
`capacity.json` — сохранённый статический расчёт этого профиля.

## Допуск и откат

`./deployment/final/rehearse.sh checker`, `combined`, `soak` создают
изолированный тестовый проект; сценарий использует синтетические сервисы
с одним GET на сервис, а не реальную нагрузку финальных чекеров.
На целевой VM требуется отдельный прогон с тремя настоящими сервисами
на каждом вулнбоксе 4 vCPU / 4 GiB и включёнными метриками.
Проверить длительность каждого раунда, CHECK/PUT/GET, p95/p99 чекеров,
очередь, CPU/RSS, OOM, DB pools/WAL, свободную память, задержки и потери
пакетов Router/Zeek и доступность Grafana. Приоритет — сохранность игры;
прошедшие синтетические тесты не дают автоматического допуска.

Для отката до игры восстановить сохранённый приватный `.env` и пересоздать
контейнеры. Эта настройка не меняет схему БД и не удаляет данные.
Итоги уже проводившихся прогонов и их ограничения — в `validation.md`.
